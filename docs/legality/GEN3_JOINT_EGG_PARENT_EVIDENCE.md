# Gen III joint ordinary egg witness — parental move history + inherited IVs

**Problem solved (bounded):** independent four-slot egg moves and six-draw IV inheritance witnesses must NOT be joined when they refer to two different hypothetical fathers or mothers. Pinned generated game-specific egg move tables, parental four-slot ordering, Light Ball controls, and the distinct RS/FRLG-versus-Emerald LCRNG inheritance behavior are each retained by delegating to the existing audited stage helpers.

`Gen3JointEggCandidateEvidence` now accepts **one explicit pair** of parent IDs, original four moves, original six-stat IVs, and an independently supplied post-inheritance six-draw RNG state. It requires the same father/mother IDs in both subproofs. Missing egg group/parent species eligibility, one missing parent-IV snapshot, unverified RNG state, or unsupported Gen IV egg-IV algorithm all produce distinct Unknown/Unsupported outcomes; no alternate generation formula is invented.

The conditional checker separates impossible hypothetical move lists, impossible known IV-stage observations and out-of-domain candidate inputs. A result of `KnownCandidateConsistent` means that **one fully supplied scenario** matches, **not** that the historical parents and RNG state truly existed or can be recovered from the stored child. A native PK3 contains none of those full historical parent identities or RNG stages.

Host and sanitizer tests cover same-parent moves/IVs, switched father and mother IDs, partial evidence, source game routing, inherited-IV mismatch, malformed >31 values, and moveset contradiction. Existing 24 forward/reverse synthetic retail vectors remain independent evidence. This interface is read-only and never issues global Invalid or mutates saves.

## Parent-pair timestamp / snapshot coupling

Parent IDs alone can accidentally combine a father's moveset from one time with an incompatible earlier/later original IV snapshot. The joint checker now requires an **independently attested nonzero shared parent-stage token** for both evidence inputs. Missing stage linkage is Unknown; mismatched stage tokens mark the asserted joint witness incoherent. Tokens are hypothetical supplied provenance, **not** stored native PK3 fields or newly inferred historical proof.

## BREED-002 physical daycare deposit order (2026-10-11)

The joint helper now requires an independently verified mapping of daycare **slot 0** and **slot 1** to the already verified parent IDs, rather than silently treating the move-donor father as physical slot 0. Unknown or missing deposit order returns `UnknownDaycareSlotOrder`; duplicated, alien or contradictory IDs return `IncoherentDaycareSlotOrder` for that proposed history. Source-attested reversed deposit order is valid and preserves the original father/mother move inheritance roles.

The regression checks 24 source-cross-checked Gen III six-draw IV stage vectors (Emerald, Ruby, FireRed) with both possible role placements, plus explicit missing, duplicate and alien slot mappings: 48 positive conditional joint histories, 48 each of four negative/unknown controls. This is **not** proof that real parent identities or a final RNG state can be reconstructed from a detached PK3, and no new global Invalid decision is connected to this helper.

## BREED-003 conditional pair-eligibility and donor-role adapter

`Gen34BreedingPairEligibility` adds an independently authored, pure, read-only helper for **explicit supplied parent snapshots**. With verified source-version personal egg groups, derived gender, full OT IDs and parent identities, it determines retail compatibility (0/20/50/70), the breeding move father/mother role and an optional explicitly attested physical daycare order. The separate `proofFor` bridge only grants the existing `PairProof::IndependentlyCompatible` to the same donor IDs; an incompatible source-attested pair remains only candidate-locally contradicted. OT not known leaves the exact compatibility score unknown even where pair eligibility is established.

The implemented gate is intentionally limited to inspected/tested Emerald, Platinum and HGSS source families. Ruby/FireRed/DP, the game-specific personal/form lookup, parental PID-derived genders, incense, offspring lineage and actual parent-save extraction are **not** claimed. The adapter does not manufacture a parent's native source fields, pass its rate off as an egg probability, or automatically infer daycare deposit order. Host/sanitizer regressions exercise both slot permutations, second egg-group overlap, Ditto combinations (including genderless), full 32-bit OT comparison, unknown metadata, duplicate IDs, Undiscovered, two Dittos, same-sex/disjoint groups and compatibility-score tiers.

### Integrated attested-pair pathway

`Gen3JointEggCandidateEvidence::evaluateFromAttestedDaycare` derives an existing four-slot move-history pair proof and ordered IV donor slots from **one independently supplied physical daycare parent record**, overriding an unverified caller-provided role order. The Emerald cross-product checks positive and reversed deposit orders plus missing deposit-order/group data and a source-backed incompatible candidate pair. Ruby/FireRed continue using the explicit conditional IV slot API until separate parent-eligibility retail execution is validated. This remains a conditional candidate-level API, not a global legality verdict or a reconstruction of lost parents from native PK3.

## BREED-003: read-only native encrypted PK4 parent snapshot projection

The separate `Gen4NativeBreedingParentEvidence` helper accepts **checksum/sanity-valid immutable native PK4 records** plus explicitly attested source game, chronological parent-snapshot identities, daycare deposited-slot order and **source-version/species/form-matched egg-group evidence**. It projects the actual persisted Gen IV gender and **full 32-bit original trainer ID** alongside the native species into `Gen34BreedingPairEligibility`, without treating an originVersion from a traded Pokémon as a daycare save's game. It supports directly modeled Platinum and HeartGold/SoulSilver families, not a guessed DP/Ruby/FRLG adapter.

Encrypted PK4 production-reader regression fixtures cover both deposit orderings, same lower 16-bit OT with distinct upper 16 bits, original Platinum records in an HGSS source, checksum tampering, egg records, gender sentinel 3, wrong family, unattested source/stage, group-species/form/game identity mismatches, duplicate snapshot IDs and source immutability. The existing Gen IV personal tables do **not** contain egg groups; those must remain externally provided and independently verified. Native snapshots by themselves do not prove historical deposit into a daycare, a parent timeline, offspring lineage, or a legitimate egg. The helper is evidence-only and cannot produce global Invalid or mutate source/staged Pokémon.

## RNG-003 — ordinary Gen IV retail IV-stage replay

`Gen4EggIVInheritanceStage` is a separate, pure, bounded Platinum/HGSS six-stat inheritance-stage evaluator. It does **not** reuse the Gen III unconditional six-draw rewind for HGSS. Platinum retains indexed position-removal and repeated-stat behavior (6 calls); HGSS removes actual selected stats and consumes 6/4/5 calls for zero/one/two Power-item holders. Power items 289–294 are mapped by their verified individual IDs; even duplicate Power items require the initial holder-selection draw. The original source's physical deposited-slot order is kept independent of move-parent roles. Independently supplied final RNG state, initial child IVs, original parent IVs and (for HGSS) both parental held-item histories are required for a verified candidate. Unavailable evidence remains Unknown; a contradicted candidate is never globally Invalid.

The separate host + sanitizer test target checks **all 138 detailed original-retail-source/independent-model cross-checked stage fixtures** in research-only PR #252 packet RNG-003: selected stats, donor slots, draw values/count, resulting six IVs, final seed, bounded rewind, hypothetical mismatch, loss of independent parent/order/initial/item/RNG evidence and malformed IVs. These are synthetic stage vectors, not true native eggs. The larger 25,382-source-comparison matrix is reproduced by the research tool; the implementation's checked-in regression covers its pinned subset. Gen IV exact DP source, PID/Everstone, initial-IV construction and complete event/history reconstruction remain out of scope.

## Gen IV joint *native* parents + moves + Power-item IV stage (2026-10-11)

`Gen4JointEggCandidateEvidence` links the previously separate read-only, verified native encrypted-PK4 parent projection, version-specific pair eligibility/donor roles, actual same-stage stored parent four-slot move lists and physical deposited IV/held-item slots, and Platinum/HGSS known-final-state IV replay. Three independently attested nonzero snapshot-stage tokens must match across native daycare, move-parent and IV witnesses, preventing false-positive cross-time joins. The source-evaluated eligibility **overrides any supplied pair-proof claim**. Actual parent move arrays, species and IDs are checked against the immutable records rather than copied from unrelated hypotheses. Source-game, egg group/row provenance and physical slot order must all be independently verified. The candidate's observed moves, base-move history, stage initial IVs, collection-time held items, final RNG state and stage timing remain independently supplied. For HGSS, historical held-item snapshots are mandatory; Platinum replay ignores Power-item contents. None of these historical fields is recoverable merely from the resulting child PK4.

Native production-reader tests execute 30 full conditional cases (three supported game IDs × two physical deposit orders × five held-item branches), with individual candidate negatives for wrong move-donor identity, borrowed parent moves, contradictory stage tokens, missing source/egg groups/deposit order, unknown initial/observed child IVs, unknown held-item histories, missing RNG, malformed IVs, wrong observation, incompatible pair and impossible observed moves. These are test-constructed valid encrypted native PK4 parent records, not historical retail save couples; they cannot prove a real egg, entire PID/rejection timeline, or a globally Invalid child. DP remains unimplemented absent direct corroboration. No writes or automatic fixes.

### Independently attested native unhatched child join

`evaluateWithNativeEgg` additionally requires a strictly valid checksum/sanity native encrypted **unhatched** PK4, a verified containing-game source family, and an independently attested original egg-stage snapshot. Its own species, four persisted move slots and six IVs must exactly match those of the proposed historical child, preventing borrowed or contradictory child observations. Malformed, hatched, missing-source or not-attested children remain Unknown; conflicting source-backed egg observations are incoherent for this candidate alone. Tests assert exact encrypted source byte preservation, mismatched move/IV history, lack of egg flag, absent original snapshot and absent source context across the joint matrix. This does not recover lost historical snapshots from today's evolved Pokémon or imply globally Invalid origin; it is a conditional proof component.

**Child chronology hardening:** The original unhatched PK4 proof now additionally requires its own independently sourced nonzero historical daycare-event token equal to the candidate's verified parent-stage token. Missing token remains Unknown; an egg from a different attested daycare event is incoherent, even if species, moves and IVs happen to match. This prevents positive cross-event child joins without asserting any native PK4 field records the lost stage token.

**Unknown-versus-incoherent distinction:** A checksum-valid unhatched PK4 does not independently certify that caller-supplied child IV observations belong to the original stage. `evaluateWithNativeEgg` explicitly returns `UnknownObservedChildIVs` when that external evidence is missing, not a false contradiction; only an independently attested mismatch is `IncoherentNativeEggRecord`. An encrypted-native regression guards this distinction.

## BREED-004 — Exhaustive *candidate-set* discipline, not global illegality

`Gen4EggCandidateUniverse` analyzes up to eight independently identified **alternative histories for the same original encrypted unhatched PK4**. It requires exact original source-game family attestation and byte-for-byte same original encrypted egg identity for every candidate record. Repeated/zero route IDs, absent archive/source evidence, unsupported family, missing child chronology, incomplete method coverage and bounded-capacity overrun are separately represented as Unknown states; they never justify a false Invalid.

A positive conditional parent+egg+IV history wins even if other alternative histories were never enumerated. An all-contradicted result exists only when **every independently grounded source candidate has complete independently attested method history**, the external daycare enumeration is independently declared complete, and each source-grounded history was contradicted by the existing joint egg-stage validator. Its `AllAttestedDaycareHistoriesContradicted` label deliberately says **daycare histories**, not all original Pokémon origins, all game versions, and certainly not global Invalid. Non-daycare, migrated, gift/event and missing-archive families are not enumerated here. Tests cover 30 native three-alternative sets and the interaction of positive evidence, source gaps, bounded search, duplicate IDs, different babies, contradictory Power-item IV sequences and independent negative-proof completeness. No source/staged writes or automatic fixes.
