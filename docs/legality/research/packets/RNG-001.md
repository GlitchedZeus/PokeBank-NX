## Retail algorithms and exact differences

Emerald chooses three IV indices using successive upper-16 outputs of `s = (0x41C64E6D*s + 0x6073) mod 2^32`, then three donor-parent bits. Its retail removal routine removes **position i**, not the chosen position. The compacted array retains its stale tail. Ruby/FireRed instead pass the **selected stat value as an array index**, which can also remove the wrong entry after compaction. Never enable the decompilation's optional BUGFIX for legality evidence. Platinum's inspected inheritance loop uses the Emerald-style removal. HGSS removes the selected position correctly and can force one of the three stats via Power items.

Pseudocode for the verified III inheritance stage:

```
available = [HP, Atk, Def, Speed, SpAtk, SpDef]
for i in 0..2:
    chosen[i] = available[next16() % (6-i)]
    remove_index = i if Emerald else chosen[i]   # retail behavior
    available[remove_index] = sentinel
    compact non-sentinel values into front; leave tail untouched
for i in 0..2: parent[i] = next16() % 2
for i in 0..2: child[chosen[i]] = parents[parent[i]][chosen[i]]
```

Parent assignments happen after all three selections. Repeated selections can overwrite a previous inheritance. “Exactly three distinct inherited IVs” is therefore not a valid universal rule.

Emerald creates the pending personality separately, with Random2 seeded from the vblank counter, and a female/Ditto Everstone route. The nature-search loop has a bounded fallback. HGSS allows either Everstone-holding parent, with selection if both hold one. Its pending PID uses MTRandom. Pt/HGSS later apply up to four ARNG/PRandom shiny retries for differing parent languages; initial PID + four attempts is at most five candidates. Nature after this transformation must not be forced to equal the Everstone parent's nature. Parent language and the original pending PID are not stored in the child.

## Required inputs / seed reconstruction

For the verified stage: LCRNG state immediately before `InheritIVs`, six initial child IVs, two parental IV vectors and exact game. To reverse with real parents, enumerate index/donor masks and require non-overwritten IV bits to fit the random-generation frames; reverse/forward validate the full call schedule. With no parents, inherited fields are free variables, so a final IV tuple generally does not identify a unique seed. Do not report a normal Method-1 failure as an egg contradiction.

This tranche does **not** provide a full egg PID+IV reverse solver. The deterministic vectors start at a documented internal boundary after initial child creation; the pending PID/MTRNG/vblank relationship remains unresolved. Full reversal requires the game-specific initial-creation calls plus the separate pending-PID stage.

## Executed positive / contradictory vectors

Run `python scripts/reproduce_inheritance.py /path/to/research-sources`. The independent Python model is checked against unchanged C `RemoveIVIndexFromList` and `InheritIVs` extracted from three pinned repositories into temporary files. **24 cases pass** (8 seeds × 3 sources). `evidence/inheritance-vectors.json` records every draw, selected stat, donor, output and final state. Parents use [30]*6 and [31]*6; child baseline is [0]*6. These are **synthetic stage inputs**, not proven complete native Pokémon.

A contradictory vector is the same known input state/parents with any final inherited value changed; it fails that exact history. It cannot prove a Pokémon globally Invalid when parents/seed are unknown. The catalog explicitly preserves this distinction. A control algorithm that removes the chosen position differs from retail for some seeds and must not replace it.

## Integration / acceptance
